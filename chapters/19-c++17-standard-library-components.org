** std::optional -I

- A new library *type* that can be used when a function may or may not return a value
- If it does not return a value, a common way is to compare with a
  predefined value such a 0, nullptr, true/false, etc
- This leads to different kinds of checks for different types
- /std::optional<T>/ can represent a type that may or may not contain a value
  - often called a *nullable type*

*Properties*
- No value is represented by /std::nullopt/
- /std::optional/ is a value type - so, it can be copied through deep copy
- Does not need to allocate any memory on heap
- You cannot store references inside /std::optional/
- Provides several overloaded operators and functions to access the value inside safely
- May throw /std::bad_optional_access/

** std::variant - I

- /std::variant/ is a *type-safe* replacement for *union* type
- Just like union, it uses the storage of the largest member
- The first memeber is always *default initialized* if variant is
  default constructed
- Alternatively, you can initialize any member of the variant during construction
- Members are destroyed properly (in contrast to union)
- Throws /bad_variant_access/ on invalid acces

** std::any

*Type Safety*
- C++ is a strongly typed language
- Object are declared with specific type and that cannot be changed later
- In some cases, we may require an object that should hold values of different types
- This is difficult to achieve in C++, except through /void */
- However, such pointers have a certain disadvantage
  - Not typesafe
  - No way to know the type
  - Cannot access the value in a type-safe way
  - Need to manage the object lifetime

*std::any*
- C++17 introduced std::any
- A *wrapper* that can hold value of any arbitrary type in a *type-safe* way
- Replacement for /void */
- Contains both the value & its type
- The value is accessed throuhg /any_cast<>/
- May allocate memory on the heap
- Throws exception of type /bad_any_cast/ on wrong type access

** std::string_view - I

*std::string_view*
- Allows us to deal with charachter sequenceis without allocating memory
- Can be considered as a kind of reference to a charachter sequence
- Can be used where ever a *non-modifialbe string* is required
- It simply stores a pointer to the character array along with its length
- It is fast an cheap to copy
- However, it should be used carefully as it can lead to bugs

*Properties:*
- Underlying sequence is *read-only*
- It can be accessed through /data()/ method
  - may return *nullptr*
  - a charachter sequence with or without null terminator
- You can only assign a new value, swap values and shrink it to a
  subset of character sequence
- Character sequence is *not guaranteed* to be *null-terminated*
  - consequently, *may* not work with C string functions
- No allocator support (because of read only)

** std::string_view - II

*When to use std::string_view*
- Don't pass in functions that accept a C-style string because it might not have a null terminator
- Do not return sting view to string from a function
- Do not assign temporary strings to string views
- Avoid as class members

** Parallel Algorithm - I

- May STL algorithms by default execute serially
- C++17 provides overloads to these algorithms that can now execute parallelly
- Algorithms that can be parallelized accept a new template parameter called *execution policy*
  - used to disambiguete the calls to overloads of the algorithm
- This can be used to inform the algorithm if it should execute *serially* or *parallelly*
- The internal implementation details are hidden to the user


*Syntax*
- Parallel versions of STL algorithms have a simple interface
- They are providedas overloaded funcitons with the first parameter signifying the execution policy
- Execution policy defines how the algorithm should execute

  /std::algorithm(execution_policy, / * begin, end, other args * / );/

*Execution Policies*
- All execution policies existing in /<execution>/ header and in /std::execution/ namespace
- Each of the policy is an individual type
- /sequend_policy/ - *seq*
  - the algorithm's execution will not be parallelized and will
    perform operations sequentially element by element
  - same as invoking the algorithm from C++14
- /parallel_policy/ - *par*
  - indicates the algorithm should execute parallelly
  - might use thread from a thread pool for execution along with the calling thread
- /parallel_unsiquenced_policy/ - *par_unseq*
  - indicates the execution may be parllelized, vectorized or migrated
    across threads

*Exception Handling*
- If an element access function throws an exception which is not
  handled, all parallel algorithm call /std::teminate/
- This also applies if sequential execution policy is chosen
- If you want to handle exceptions, use the *standard* algorithms instead
- Parallel algorithms themselves may throw /std::bad_alloc/ if they fail
  to acquire memory during execution

*Parallel Algorithms Everywhere?*
- Backward compatability
- Can use both input & output iterators
- Synchronization is expensive
- Parallelized algorithms teminate on exceptons, sequenced do not
- Do not give good performance for operations on small number of
  elements due to *overhead*
-
